## event_model.py

import sqlite3


def insert_event(
    timestamp,
    username,
    source_ip,
    event_id,
    event_type,
    message
):
    conn = sqlite3.connect("siem.db")
    cursor = conn.cursor()

    cursor.execute(
        """
        SELECT id
        FROM events
        WHERE timestamp = ?
        AND username = ?
        AND source_ip = ?
        AND event_id = ?
        AND event_type = ?
        AND message = ?
        """,
        (
            timestamp,
            username,
            source_ip,
            event_id,
            event_type,
            message
        )
    )

    existing_event = cursor.fetchone()

    if existing_event:
        conn.close()
        return False

    cursor.execute(
        """
        INSERT INTO events (
            timestamp,
            username,
            source_ip,
            event_id,
            event_type,
            message
        )
        VALUES (?, ?, ?, ?, ?, ?)
        """,
        (
            timestamp,
            username,
            source_ip,
            event_id,
            event_type,
            message
        )
    )

    conn.commit()
    conn.close()

    return True


def get_events():
    conn = sqlite3.connect("siem.db")
    cursor = conn.cursor()

    cursor.execute(
        """
        SELECT id, timestamp, username, source_ip,
               event_id, event_type, message
        FROM events
        ORDER BY id DESC
        """
    )

    rows = cursor.fetchall()

    conn.close()

    return rows

### Explanation

This file manages how security events are written to and retrieved from the SQLite database.

#### `insert_event()`

This function receives a normalized security event and stores it in the `events` table.

The function accepts:

- timestamp
- username
- source_ip
- event_id
- event_type
- message

#### Duplicate Event Check

Before inserting a new event, the function checks whether the exact event already exists.

This prevents the same log entry from being stored repeatedly when the log parser is run more than once.

The function returns:

```text
True = new event inserted
False = duplicate event skipped
```

That return value is important because the log parser only runs detection logic for newly inserted events.

#### `get_events()`

Retrieves stored events from SQLite.

Events are returned in descending order so the newest records appear first.

## detection_rules.py

import sqlite3
from datetime import datetime, timedelta
from alert_model import insert_alert


def check_failed_login_rule(username):
    conn = sqlite3.connect("siem.db")
    cursor = conn.cursor()

    cursor.execute(
        """
        SELECT timestamp
        FROM events
        WHERE username = ?
        AND event_type = 'Failed Login'
        ORDER BY timestamp DESC
        """,
        (username,)
    )

    rows = cursor.fetchall()
    conn.close()

    if len(rows) < 5:
        return False

    latest_time = datetime.strptime(
        rows[0][0],
        "%Y-%m-%d %H:%M:%S"
    )

    five_minutes_ago = latest_time - timedelta(minutes=5)

    recent_failures = 0

    for row in rows:
        event_time = datetime.strptime(
            row[0],
            "%Y-%m-%d %H:%M:%S"
        )

        if event_time >= five_minutes_ago:
            recent_failures += 1

    if recent_failures >= 10:
        insert_alert(
            rows[0][0],
            username,
            "Repeated Failed Logins",
            "High",
            "10 failed logins detected within 5 minutes"
        )

        return True

    elif recent_failures >= 5:
        insert_alert(
            rows[0][0],
            username,
            "Repeated Failed Logins",
            "Medium",
            "5 failed logins detected within 5 minutes"
        )

        return True

    return False


def check_account_lockout_rule(
    timestamp,
    username
):
    insert_alert(
        timestamp,
        username,
        "Account Lockout",
        "High",
        "Windows account lockout detected"
    )

    return True

### Explanation

This file contains the main security detection logic.

It is the part of the project that converts normal authentication events into security alerts.

#### `check_failed_login_rule(username)`

This function checks failed-login activity for a specific user.

It queries the database for:

```text
event_type = Failed Login
```

and only retrieves events associated with the supplied username.

#### Five-Minute Time Window

The newest failed-login timestamp is identified.

The code then calculates:

```python
latest_time - timedelta(minutes=5)
```

This creates the beginning of the five-minute detection window.

The remaining failed-login events are checked to determine how many occurred inside that window.

#### Medium Severity Threshold

```text
5–9 failed logins within 5 minutes
```

creates:

```text
Medium
Repeated Failed Logins
```

#### High Severity Threshold

```text
10+ failed logins within 5 minutes
```

creates:

```text
High
Repeated Failed Logins
```

The High threshold is evaluated first.

This is important because ten failed logins also satisfy the condition of being greater than five. Checking High first prevents a ten-login sequence from being incorrectly classified as Medium.

#### `check_account_lockout_rule()`

Creates a High severity alert when an account lockout event is detected.

Windows Event ID:

```text
4740
```

represents an account lockout.

### Detection Flow

```text
Authentication Events
        ↓
Detection Engine
        ↓
Count Failed Logins
        ↓
5–9 → Medium
10+ → High

Account Lockout
        ↓
High Alert
```

### Why This Matters to a SOC Analyst

Instead of manually reviewing every login event, the SIEM correlates related activity and raises alerts when predefined suspicious patterns occur.

    check_failed_login_rule,

def parse_log_file(filename):
    with open(filename, "r") as file:
        for line in file:
            line = line.strip()

            if not line:
                continue

            parts = line.split("|")

            timestamp = parts[0]
            username = parts[1]
            source_ip = parts[2]
            event_id = parts[3]
            event_type = parts[4]
            message = parts[5]

            inserted = insert_event(
                timestamp,
                username,
                source_ip,
                event_id,
                event_type,
                message
            )

            if not inserted:
                continue

            if event_type == "Failed Login":
                check_failed_login_rule(username)

            elif event_type == "Account Lockout":
                check_account_lockout_rule(
                    timestamp,
                    username
                )

    print("Logs imported successfully")


parse_log_file("sample_windows_logs.txt")

  const [alerts, setAlerts] = useState([])
  const [eventFilter, setEventFilter] = useState('All')
  const [alertFilter, setAlertFilter] = useState('All')

    fetch('http://127.0.0.1:8000/events')
      .then((response) => response.json())
      .then((data) => setEvents(data))

      .then((response) => response.json())
      .then((data) => setAlerts(data))

The dashboard uses `useState()` to store application data.

The following state variables are used:

```text
events
alerts
eventFilter
alertFilter
```

`events` stores authentication events retrieved from the backend.

`alerts` stores generated SIEM alerts.

`eventFilter` tracks which event type the analyst wants to view.

`alertFilter` tracks which alert type or severity the analyst wants to view.

#### Retrieving Data with useEffect()

When the dashboard loads, `useEffect()` automatically sends requests to the FastAPI backend.

The dashboard retrieves data from:

```text
GET /events
GET /alerts
```

The returned JSON data is stored in React state.

This allows the dashboard to display live data from SQLite rather than relying on hard-coded values.

#### Dashboard Metrics

The dashboard calculates several metrics from the API data:

- Total Events
- Active Alerts
- High Severity Alerts
- Medium Severity Alerts

High severity alerts are calculated by filtering alerts where:

```text
alert.severity === "High"
```

Medium severity alerts are calculated using the same approach.

#### Event Filtering

The dashboard allows analysts to filter events by:

- All Events
- Failed Login
- Successful Login
- Account Lockout

When a filter is selected, React creates a filtered event list.

If "All Events" is selected, every event is displayed.

Otherwise, only events matching the selected event type are shown.

#### Alert Filtering

The dashboard allows analysts to filter alerts by:

- All Alerts
- High Severity
- Medium Severity
- Account Lockout
- Repeated Failed Logins

Severity filters compare:

```text
alert.severity
```

Alert-type filters compare:

```text
alert.alert_type
```

This allows analysts to focus on specific security events.

#### Alert Severity Visualization

Chart.js is used to display the distribution of alert severity.

The chart compares:

- High severity alerts
- Medium severity alerts

This provides a quick visual overview of the current alert environment.

#### Recent Alerts Table

The Recent Alerts table displays:

- Timestamp
- Username
- Alert Type
- Severity

The newest alerts are displayed first.

#### Recent Events Table

The Recent Events table displays:

- Timestamp
- Username
- Source IP
- Event Type

This provides visibility into the underlying authentication activity.

### Frontend Data Flow

```text
SQLite Database
        ↓
FastAPI
        ↓
GET /events + GET /alerts
        ↓
React State
        ↓
Metrics
Filters
Chart.js
Tables
        ↓
SOC Analyst
```
